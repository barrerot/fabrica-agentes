# F3 — Logins y cuentas

## Objetivo

La persona acredita Claude por login individual o token largo, según el cuestionario.
F2 usa creado: modelo vacío y canales sin credenciales, sin leer el registro.
Después de los logins, F5 usa acreditado: modelo vigente exacto y golden sin
credenciales; admite credenciales en canales sin exigirlas de nuevo.
El modo histórico sin argumentos (alias preparado) exige canales sin
credenciales y no se usa en las fases. Los checks del instalador proporcionan
el entorno cerrado; no ejecutes verify.sh directamente desde esta terminal.

## Precondiciones

F2 verde. Usuarios y contenedores existen. Cada cuenta debe tener capacidad.
M1 necesita CodeRabbit CLI instalado y comprobable con coderabbit --version.
Fija los nombres públicos desde las respuestas, nunca cargues el env.

## Pasos

```bash
CEO="$(sed -n 's/^usuario_ceo=//p' "$R")"
C1="$(sed -n 's/^usuario_c1=//p' "$R")"
M1="$(sed -n 's/^usuario_m1=//p' "$R")"
OPERADOR="$(sed -n 's/^usuario_incus=//p' "$R")"
CUSER="$(sed -n 's/^cuser=//p' "$R")"
MAQUINA="$(sed -n 's/^maquina_n=//p' "$R")"
PROYECTO="$(sed -n 's/^proyecto=//p' "$R")"
N=1
CARRIL="${MAQUINA}${N}"
CONTENEDOR="vibe-channel-$CARRIL"
export AM_LEDGER="$PKG/ledger/cuentas.json" TF_ROOT="$PKG" TF_MANIFEST="$PKG/manifiestos/$PROYECTO.conf"
```

En la terminal de CEO, la persona ejecuta claude login y gh auth login.
Este es el modo claude_auth=login. Si eligió claude_auth=token, omite los logins
de Claude de esta guía: ejecuta claude setup-token en SU terminal por cada cuenta
y entrega cada token al lector oculto, identificado por alias de pozo:

```bash
! bash "$PKG/instalacion/scripts/f3-acreditar.sh" --leer
bash "$PKG/instalacion/scripts/f3-acreditar.sh" --plan
! sudo bash "$PKG/instalacion/scripts/f3-acreditar.sh" --ejecutar
```

El plan requiere visto bueno. Guarda tokens por alias en escrow/tokens, modo
0600; los distribuye por stdin usando token_env_write del paquete. Los roles
usan el primer alias; los canales los asignan en orden circular y cada pozo
recibe su alias del ledger. No relanza sesiones: F5 las crea después.
El perfil runner no recibe token, login de gh ni env operacional.
Nunca entregues tokens por argumentos, chat ni paneles. No vuelques el entorno
ni los ficheros de credenciales; comprueba solo nombres y presencia.

Antes de F5, instala en el host el mismo artefacto CodeRabbit de la plantilla,
con versión y sha256 de la fuente única del paquete. Muestra el plan, espera
visto bueno y ejecuta con privilegios:

```bash
bash "$PKG/instalacion/scripts/f3-coderabbit.sh" --plan
! sudo bash "$PKG/instalacion/scripts/f3-coderabbit.sh" --ejecutar
```

En modo login, para C1 y M1 abre una terminal con cada usuario (sudo -iu "$C1" y
sudo -iu "$M1") y ejecuta claude login. Cierra cada terminal con exit.
No copies .credentials.json entre roles ni pozos.

Antes de enviar el env operacional y configurar autostart del contenedor,
muestra y aprueba el plan. Los panes se preparan en F5:

```bash
bash "$PKG/instalacion/scripts/f3-canales.sh" --plan
! sudo bash "$PKG/instalacion/scripts/f3-canales.sh" --ejecutar
```

Por cada canal, fija N desde 1 hasta canales_n y recalcula CARRIL/CONTENEDOR
con las dos asignaciones del bloque. En modo login, la persona abre terminal
con el operador, entra como CUSER y ejecuta claude login; sale con exit.
GitHub y git se acreditan por el envío aprobado, también en modo token.

```bash
! sudo -H -u "$OPERADOR" incus exec "$CONTENEDOR" -- su - "$CUSER"
claude login
exit
```

Si codex=si, la persona hace codex login en el host y mueve la única cuenta:

```bash
codex login
bash "$PKG/skills/talent-channels/scripts/auth-move.sh" move codex1 "host:$HOSTNAME" "channel:$CONTENEDOR" --agent codex
bash "$PKG/skills/talent-channels/scripts/auth-move.sh" status
```

Solo un endpoint a la vez. Para mover al siguiente usa el canal actual como
from. No duplicar auth.json. Si codex=no, AUD=Claude ya está declarado.
Los pozos se crearon en F2 a partir de las claves de pozos en el ledger;
no se supone un número fijo. La persona consulta solo esos ids públicos,
en modo login abre cada pozo como CUSER y ejecuta claude login con la cuenta de su alias:

```bash
jq -r '.pozos | keys[]' "$PKG/ledger/cuentas.json"
! sudo -H -u "$OPERADOR" incus exec POZO -- su - "$CUSER"
claude login
exit
```

La persona sustituye POZO por cada id leído. El check hace una petición
pequeña que debe completar correctamente para acreditar capacidad del pozo; no muestra
su respuesta ni credencial. Para consumirlo usa MOVE y su alias declarado:

```bash
bash "$PKG/skills/talent-channels/scripts/auth-move.sh" move ALIAS "pool:POZO" "channel:$CONTENEDOR" --agent claude
```

Un pozo consumido se acredita por el health-check y grant durable de MOVE.
Nunca poner correos o credenciales en las respuestas públicas ni copiar logins.

## Comprobación

```bash
bash "$PKG/instalacion/scripts/check-F3.sh"
```

El envío usa push-carril-env del paquete para canales: instala el env,
gh auth login --with-token y gh auth setup-git. Configura también git para cada
rol del host. El check pide «Responde solo: OK» usando login o token privado
0600 y acredita rc 0, un objeto JSON válido, is_error false, subtype success
y result cadena no vacía. No compara la respuesta con ninguna palabra.
Exige también gh auth status y git ls-remote origin dentro de canales;
en el host consulta la URL declarada antes de crear los clones de F4/F5.
Se excluye al runner por su perfil declarado en channel-profiles.list.
El diagnóstico identifica el rol o contenedor si falta credencial o capacidad.
Tras esta acreditación, F5 ejecuta resolver-modelos.sh bajo cada usuario de rol:
el registro es privado por usuario, sin copiarlo entre roles. Una resolución
fallida detiene F5; la guía F5 indica cómo restaurar la capacidad y repetirla.
En modo token, f3-tokens entrega credencial a CEO, C1 y M1, canales y pozos;
no al usuario operador Incus. En modo login tampoco se pide login de ese
operador. F5 resuelve solo los tres roles: no crea su registro. El doctor
actual lo exige para canales; véase en F5 la propuesta de consultar el registro
de C1 y el bloqueo que permanece hasta resolver esa autoridad.
F7
comprueba el ejecutable real del pane del auditor.

## Remediación

| Diagnóstico | Acción |
|---|---|
| login Claude ausente o modo | Ejecutar login en la terminal del usuario indicado; restaurar 0600. |
| login/env ausente o modo en canal | Repetir login ahí o el envío aprobado; nunca hacerlo en golden. |
| gh sin sesión | Completar gh auth login con permisos adecuados en la terminal del rol o canal indicado. |
| git sin autenticación | Repetir el envío aprobado por push-carril-env y gh auth setup-git para el rol indicado; comprobar ls-remote. |
| CodeRabbit CLI ausente | La persona instala el CLI en el PATH de M1; no inventar un revisor sustituto. |
| auth-move rc / ledger vacío | Leer el journal con status; usar repair solo según su contrato, sin copiar auth. |
| ledger: pozos/cuentas/alias / MOVE no acreditado | Restaurar el ledger generado y completar la operación real, conservando campos desconocidos. |
| pozo login o capacidad no acreditada | Caso: sin acreditar, no hay token ni login privado válido. Hacer login en el usuario o pozo indicado y restaurar modo 0600; repetir el check real. |
| credencial rechazada | Caso: el CLI devuelve is_error true por autenticación. Renovar login o token del usuario indicado y repetir el check. |
| sin cupo ahora | Caso: el CLI devuelve is_error true por límite de uso. Esperar el restablecimiento o acreditar otra cuenta mediante MOVE; repetir el check. |
| sin respuesta en 90 s | Caso: vence el timeout de la petición. Revisar disponibilidad del CLI y conectividad en la terminal indicada; repetir el check. |
| otro error (subtype) | Caso: JSON inválido, vacío, compleción incompleta o rc no cero. Revisar el CLI en la terminal del usuario indicado; no acreditar manualmente. |
