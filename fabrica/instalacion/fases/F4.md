# F4 — Instalar el contrato del producto

## Objetivo

Dejar verdes las comprobaciones duras y la validación de instancia. Los siete
recibos manuales pueden quedar pendientes: el ensayo ocurre en F8. Esto todavía
no certifica el repositorio para producción.

## Precondiciones

F3 verde, cuestionario completo, CLON terminado en el nombre de repo_url.
La persona tiene permisos de administración del repositorio GitHub.

## Pasos

En la terminal del instalador recupera el contexto público. Sustituye PKG por
la ruta absoluta permanente real:

```bash
PKG=/srv/fabrica/talent-factory
R="$(sed -n 's/^respuestas=//p' "$PKG/instalacion/estado/contexto.conf")"
H="$(sed -n 's/^home=//p' "$PKG/instalacion/estado/contexto.conf")"
CLON="$(sed -n 's/^clon=//p' "$PKG/instalacion/estado/contexto.conf")"
URL="$(sed -n 's/^repo_url=//p' "$R")"
PROYECTO="$(sed -n 's/^proyecto=//p' "$R")"
REPO="${URL#https://github.com/}"
REPO="${REPO%.git}"
git clone "$URL" "$CLON"
bash "$PKG/instalacion/adjudicar-identidad.sh" --salida "$PKG" --home "$H" --destino "$CLON"
```

Si el clon existe, omite únicamente git clone. La adjudicación rc 4 sigue roja
y restaura el destino: resolver validación de instancia, sin cambiar invariantes. M1 necesita clon
propio con escritura sobre ficheros y .git; no compartir un checkout mutable.

La adjudicación usa el manifiesto generado para esta instalación e ignora
manifiestos/ejemplo.conf únicamente si conserva exactamente el ejemplo distribuido.
Con cero o varios candidatos se detiene con rc 2 y los enumera. Instala por miembro
los skills ausentes y conserva los skills propios con otros nombres. Reconoce cada
miembro por su núcleo idéntico al paquete, excluidos los overlays declarados.
Revisa todos los miembros y enumera los distintos: otro skill con el mismo nombre,
o una versión anterior o modificada de este paquete. Antes de sustituir, la persona
revisa y guarda su versión completa en un commit. Después repite la orden añadiendo
--sustituir skill-creator (o el miembro indicado; repetible) o --sustituir-todos.
Ambas opciones exigen versión completa en git y ausencia de cambios pendientes,
ignorados o sin seguimiento en cada miembro. La versión anterior queda en el
historial. Si falla propagación, carga o validación final, restaura el destino.

El onboarding toma los diez IDÉNTICOS del paquete y genera los EQUIVALENTES
con los gates del cuestionario y assets del skill. Muestra el plan, revisa con
la persona y ejecuta:

```bash
bash "$PKG/instalacion/scripts/f4-onboarding.sh" --plan
bash "$PKG/instalacion/scripts/f4-onboarding.sh"
git -C "$CLON" diff
```

Markdown/gitignore se fusionan por bloques; settings conserva hooks previos.
También genera docs/reference/issue-craft-perfil-<proyecto>.md desde la plantilla
de talent-issue-craft: repo, clave del equipo, gates y stack del cuestionario.
Los valores neutros restantes quedan pendientes de completar por el equipo.
El perfil entra en el plan, la fusión idempotente y el commit que llega a main.
El anexo de coordinación se monta en manifiestos/anexo-coordinacion-<proyecto>.md;
CLAUDE.md y AGENTS.md exigen leerlo antes de adjudicar canales o runners. Queda
fuera del núcleo de skills y entra en el mismo commit de F4.
El draft previo se conserva en un bloque y exige además los gates nuevos;
CodeRabbit fusiona los valores obligatorios conservando sus otras opciones.
YAML con alias, mapas inline o duplicados y hooks incompatibles requieren
fusión humana: no se interpreta configuración ambigua. La repetición es idempotente.
La identidad se instala solo en CLON/.claude/skills.

Lleva los ficheros a main ANTES de proteger la rama. Usa rama y PR también en
un repo sin protección: el hook canónico del producto reserva la subida directa
a main al sentinel del motor, que no se instala como contrato de producto.
No cambiar el hook ni inventar ese sentinel. El responsable aprueba primero el
diff y la auditoría; después ejecutar en la terminal del instalador:

```bash
git -C "$CLON" switch -c chore/contrato-fabrica
git -C "$CLON" add .githooks scripts docs .github .gitignore .coderabbit.yaml CLAUDE.md AGENTS.md .claude/settings.json .claude/hooks .claude/skills manifiestos
git -C "$CLON" commit -m 'chore(producto): instalar contrato de fabrica'
cd "$CLON"
bash scripts/audit-go.sh
bash scripts/draft-handoff.sh
git -C "$CLON" push -u origin chore/contrato-fabrica
gh pr create --repo "$REPO" --head chore/contrato-fabrica --base main --title 'Instalar contrato de fábrica' --body 'Contrato inicial y validación del producto.'
```

Tras revisar el PR y sus gates, el responsable fusiona según la política vigente:

```bash
PR=1
gh pr merge "$PR" --repo "$REPO" --squash
git -C "$CLON" switch main
git -C "$CLON" pull --ff-only origin main
```

PR se sustituye por el número recién creado. Si había protección, cualquier
check exigido debe estar verde antes de fusionar; nunca usar --admin ni bypass.
Esta instalación inicial no sustituye el ciclo de humo y los recibos de F8.
Los hooks pueden bloquear el primer push: seguir audit-go/draft-handoff sin
desactivarlos ni emitir sentinels a mano. No proteger primero un main que
todavía carece de local-gates.

Protección: documentación oficial
https://docs.github.com/en/rest/branches/branch-protection, verificada por el
coordinador el 2026-10-03, API 2026-03-10. PUT exige admin y required_status_checks,
enforce_admins, required_pull_request_reviews y restrictions; usa checks.
Enseña cuerpo y lectura actual y espera visto bueno antes de aplicar:

```bash
bash "$PKG/instalacion/scripts/f4-proteccion.sh" --plan
bash "$PKG/instalacion/scripts/f4-proteccion.sh" --ejecutar
```

Relee y compara 12 valores A2 y 4 ajustes A2b. En privado gratuito GitHub no
permite protección: declarar el pendiente procedimental y conservar el rechazo.
Un error de permisos/API no se presume plan gratuito. F4 acepta solo el rc real
0 o 3 y validación de instancia verde.

Recibos permanentes: H/.local/share/fabrica/PROYECTO/receipts. autoridades.txt
contiene ids GitHub numéricos separados por comas. Onboarding y check fijan
canon/recibos sin exports manuales. Continúa F5–F8 y después sigue la guía
DESPUES-certificacion.md para completar los siete recibos.

## Comprobación

El onboarding crea la etiqueta cr-review si falta; check-F4 la exige. F4 lee
la política existente de CodeRabbit y registra el aviso en politica-repositorio.json.
Si falta el YAML o no acredita revisión automática desactivada, la persona
elige desactivarla en la configuración de la App o aceptar el gasto de cupo.
El montaje conserva esa opción y no cambia la configuración de la App.
También enumera workflows propios del repositorio que pueden ejecutarse en
cada PR. F8 informa sus estados; exige local-gates sobre el head fusionado.

```bash
bash "$PKG/instalacion/scripts/check-F4.sh"
```

Imprime manuales pendientes con nombres y cantidad. Rc 1/2 del verificador
y cualquier rojo de validación impiden avanzar.

## Remediación

| Diagnóstico | Acción |
|---|---|
| clon ausente / origin distinto / nombre distinto | Corregir CLON contra repo_url, sin cambiar el remoto ajeno. |
| equivalente enlazado / bloque inválido | Retirar enlace con revisión; restaurar delimitadores únicos conservando contenido. |
| destino no regular / padre no directorio | Revisar las rutas indicadas con la persona, conservar su contenido y dejar los ficheros y directorios del contrato en su tipo correcto. |
| canon existente distinto | El plan muestra el diff. Aceptar cada sustitución canónica con --aceptar-canon RUTA; es repetible. Los IDÉNTICOS deben coincidir byte a byte. |
| coderabbit: YAML con alias/tabs requiere fusión humana | Fusionar conservando opciones propias y fijando reviews.request_changes_workflow: true, reviews.auto_review.enabled: true y reviews.auto_review.drafts: false. Repetir onboarding. |
| ruleset: checks ajenos / aprobaciones de revisión / regla no acreditada | Adaptar o retirar el ruleset en GitHub con decisión humana; el instalador no modifica rulesets. |
| ruleset: reglas efectivas no verificables / formato no verificable | Restaurar lectura y verificar formato; no omitir comprobación. |
| settings inválidos | Corregir JSON y arrays conservando hooks previos. |
| paridad rc 1/2 / recibo no parseable | Resolver los FAIL/ERROR literales del verificador y repetir. |
| manuales pendientes rc 3 | AVISO: conservar nombres y seguir montaje; certificar después sin darlas por cumplidas. |
| autoridades CSV inválido | Usar ids numéricos comprobados con gh api users/LOGIN. |
| autoridades enlace no permitido | Restaurar el fichero regular de ids autorizados sin seguir el enlace. |
| protección/ajustes relectura distinta o aplicación rechazada | Corregir permisos/plan/valores contra el cuerpo mostrado. |
| perfil / adjudicación / validación roja | Resolver los diagnósticos de los consumidores antes de avanzar. |

## Al terminar

Antes de escribir, el onboarding calcula las fusiones y comprueba los destinos,
permisos y diferencias canónicas. Informa todos los conflictos detectados; sin
resolverlos no escribe. Añade excepciones delimitadas a .gitignore para que
los ficheros del contrato puedan incorporarse con git add.

Ejemplo tras revisar el diff del plan y aceptar esa ruta:

```bash
bash "$PKG/instalacion/scripts/f4-onboarding.sh" --aceptar-canon scripts/github/validar-rama-pr.sh
```

Las reglas efectivas se leen de GET /repos/{owner}/{repo}/rules/branches/main.
Referencia oficial: https://docs.github.com/en/rest/repos/rules#get-rules-for-a-branch
(referencia registrada el 2026-10-04; formato vigente pendiente de verificación
en línea). Se rechazan reglas no acreditadas, checks ajenos a local-gates y
aprobaciones de revisión. No se cambia ningún ruleset.

Contrato duro instalado y validación verde; certificación manual pendiente declarada.
