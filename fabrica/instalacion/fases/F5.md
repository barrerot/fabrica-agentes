# F5 — Iniciar CEO, torre C1 y estación M1

## Objetivo

Arrancar sesiones nuevas con renderer clásico y consultas del doctor autorizadas.

## Precondiciones

F4 verde, usuarios creados en F1 y logins completos. Los actores deben poder
ejecutar Claude, recorrer los padres de PKG y CLON y leer el manifiesto público.
M1 además necesita CodeRabbit CLI instalado en su PATH.
No reutilices la identidad de la sesión instaladora como evidencia de CEO.

## Pasos

Después del PR de F4, en una terminal nueva de C1 y después de M1, crea su clon propio. Sustituye
URL y nombre por los del cuestionario; el directorio debe tener el mismo basename
de repo_url. HOME aquí es el home del rol que abrió esta terminal:

<!-- terminal: C1 -->
```bash
URL=https://github.com/org-example/producto.git
CLON_ROL="$HOME/producto"
git clone "$URL" "$CLON_ROL"
test -w "$CLON_ROL"
test -w "$CLON_ROL/.git"
```

Si ya existe, verificar su origin y conservar trabajo antes de actualizar por
fast-forward. Sus ficheros y .git pertenecen al rol; no conceder escritura sobre
el clon del CEO ni sobre instalacion/estado. Cada torre arranca en su clon propio;
las comprobaciones y las reglas sudoers consultan esa ruta.

Enseña el plan y sus reglas sudoers exactas, espera el visto bueno y después:

<!-- terminal: instalador -->
```bash
PKG=/srv/fabrica/talent-factory
bash "$PKG/instalacion/scripts/f5-torres.sh" --plan
! sudo bash "$PKG/instalacion/scripts/f5-torres.sh" --ejecutar
```

Crea ceo, torre-c1 y m1 en el usuario declarado. Aplica install-statusline,
tui=default, confianza del cwd, IS_SANDBOX=1 y
CLAUDE_CODE_DISABLE_ALTERNATE_SCREEN=1. No usa --continue ni inventa transcripts.
Fusiona hasCompletedOnboarding en .claude.json, modo 0600, conservando las demás claves.
M1 recibe .config/talent-factory/station.conf, configuración sin secretos que su
torre carga al arrancar: estación, clon propio, manifiesto, slug y usuario/ruta
del runner. El generador escribe manifiestos/runner-identity.map con el host local.
check-F5 exige que seal-suite.sh --plan resuelva la estación y su runner.
Además ejecuta la validación de correspondencia del repositorio del motor real
en el runner, sin red, gates ni publicación. Comprueba los clones de CEO, C1 y M1
limpios respecto a HEAD para todos los ficheros con seguimiento.
Con sesiones existentes solo conserva la sesión; el check debe acreditarla.

Cada rol carga .config/talent-factory/runtime.conf al arrancar. Esta configuración
pública exporta TA_BUS_STATE_DIR, TA_BUS y TA_BUS_LOCK con las rutas de su estado
y del bus común. check-F5 comprueba el contenido para CEO, C1 y M1.

La persona se conecta a cada sesión en su terminal, con los usuarios de F3:

```bash
PKG=/srv/fabrica/talent-factory
R="$(sed -n 's/^respuestas=//p' "$PKG/instalacion/estado/contexto.conf")"
CEO="$(sed -n 's/^usuario_ceo=//p' "$R")"
C1="$(sed -n 's/^usuario_c1=//p' "$R")"
M1="$(sed -n 's/^usuario_m1=//p' "$R")"
! sudo -H -u "$CEO" tmux attach -t ceo
! sudo -H -u "$C1" tmux attach -t torre-c1
! sudo -H -u "$M1" tmux attach -t m1
```

Sustituye PKG por la ruta real en esta terminal del instalador antes de conectar.
Da a CEO el rol talent-ceo; a C1 talent-coordination y talent-context; a M1
talent-merger. CEO y M1 leen su anexo de instancia desde CLON/.claude/skills.
Coordinación lee CLON/manifiestos/anexo-coordinacion-PROYECTO.md, generado
con el mismo censo y autoridad de recursos que el mando.
La sesión debe haber procesado un turno para emitir ctx. Separar de tmux
con Ctrl-b d conserva la sesión; no usar /clear.
Si aparece el aviso del modo sin permisos, «No, exit» está preseleccionado:
pulsa flecha abajo una vez para seleccionar «Yes, I accept» y después Enter.
Aceptas que Claude ejecute herramientas sin pedir permiso en cada orden.
No pulses Enter sobre «No, exit»: termina la sesión. check-F5 distingue una
sesión parada en un aviso de una sesión con contexto visible.
Nunca vuelques el entorno ni ficheros de credenciales; comprueba solo nombres.
Para reanudar posteriormente, leer la referencia de torre-resume y usar
su UUID comprobado, nunca --continue.

## Comprobación

Antes de F7, abre terminal nueva de C1 con grupos renovados. Sustituye las rutas
públicas del bloque por las reales; no lee el estado privado del CEO:

<!-- terminal: C1 -->
```bash
PKG=/srv/fabrica/talent-factory
CLON="$HOME/producto"
cd "$CLON"
CARRILES="$(sed -n 's/^TCO_DEV_CARRILES="\(.*\)"/\1/p' "$HOME/.config/talent-channel-operation/agents.conf")"
for CARRIL in $CARRILES; do
  bash "$CLON/.claude/skills/talent-channel-operation/scripts/preparar-sesiones.sh" --plan "$CARRIL"
done
```

Enseña todos los planes y espera visto bueno. USUARIO_CANAL es el cuser
declarado por el cuestionario. Después, en esa misma terminal:

```bash
USUARIO_CANAL=operador
for CARRIL in $CARRILES; do
  bash "$PKG/skills/talent-channel-operation/scripts/preparar-modelo-canal.sh" "vibe-channel-$CARRIL" "$USUARIO_CANAL" || exit 1
  bash "$CLON/.claude/skills/talent-channel-operation/scripts/preparar-sesiones.sh" --ejecutar "$CARRIL"
done
```

Sal de la terminal de C1 con exit. La comprobación final se ejecuta desde
la terminal del instalador, con PKG y el contexto privado del CEO.
El verificador de infraestructura se ejecuta mediante f2-provision.sh --verificar
desde la terminal del instalador, con el entorno cerrado de la instancia.
check-F2 lo exige antes de los logins. Desde la terminal del instalador, check-F5 acredita la preparación
de las sesiones mediante sus consultas autorizadas; no ejecutar verify.sh sin
esa configuración.

F5 acredita el CLI y resuelve
el registro bajo cada usuario de rol. CEO arranca con el Opus vigente; C1 y M1
con el Sonnet vigente. F6 instala para cada rol el cron semanal emitido por
cron-modelos.sh --linea (domingo 03:17), conservando las entradas ajenas.
La resolución de todos los usuarios termina antes de iniciar torres; un fallo
detiene la fase con el mensaje de la orden. Cada lanzamiento relee el ID completo
de su propio registro, comprueba rc y valor no vacío. check-F5 compara la etiqueta
visible mediante la librería del skill. M1 tiene listas de flota vacías; CEO
conserva las listas de supervisión que el doctor acredita.
La preparación del modelo del canal corre como C1 antes de su primer arranque.
El doctor consulta el registro propio del mando para los modelos de los canales.
El operador Incus realiza las capturas; no necesita registro ni acreditación
Claude para esa consulta. F5 comprueba capacidad y resolución de los tres roles
del host antes de iniciar las torres.
check-F5 ejecuta verify.sh --etapa acreditado con entorno cerrado y el registro privado
de C1, por ruta explícita y sin copiarlo. Usa root mediante una regla sudoers
de argumentos exactos para leer el escrow privado del CEO y comparar identidad;
registro ausente o canal sin preparar cierra la fase. F2 solo exige
modelo vacío con --etapa creado. No se copian registros entre usuarios.
acreditado mantiene las comprobaciones estructurales y exige igualdad exacta
del modelo vigente del registro. Permite credenciales Claude y Codex en los
canales sin exigir su presencia: F3 acredita su capacidad. La plantilla golden
debe permanecer sin ambas credenciales. El modo histórico sin argumentos
(alias público preparado) exige canales sin credenciales y no se usa en las
fases. creado corresponde solo a F2, antes de los logins. No ejecutes el
verificador directamente: check-F5 proporciona el entorno cerrado de la instancia.
El doctor completo corresponde a F7, después de crear bus y acreditaciones.

La igualdad exacta del ID completo se comprueba en el momento de F5, antes
del primer despacho. Después de trabajar un encargo, el selector de sesión
puede guardar el alias de familia sonnet en settings.json al confirmar
«Enter to set as default». En ese momento el doctor de F7 es la autoridad
sobre el modelo EN USO: lee la etiqueta del panel. Con F5 ya avanzada,
avanzar F6, F7 y F8 comprueba solo la fase correspondiente y no repite check-F5.
Si necesitas volver a acreditar F5, abre la terminal de C1 con PKG,
CARRILES y USUARIO_CANAL definidos como en los bloques anteriores y prepara:

```bash
for CARRIL in $CARRILES; do
  bash "$PKG/skills/talent-channel-operation/scripts/preparar-modelo-canal.sh" "vibe-channel-$CARRIL" "$USUARIO_CANAL" || exit 1
done
```

Después vuelve a la terminal del instalador y ejecuta check-F5 con el bloque
de comprobación siguiente. No sustituyas la igualdad por aceptación de alias.

F5 escribe la autenticación del CLI de CodeRabbit solo para M1 mediante el
función compartida con canales. El fichero auth.json queda 0600 y su directorio
0700. check-F5 ejecuta coderabbit auth status sin gastar una revisión; un
estado rojo cierra la fase. Las claves no se exportan al entorno de las torres.

Solo crea dev/auditor si falta sesión; verifica binarios por procesos usando
las funciones del dispatch. Conserva una sesión incompleta para diagnóstico.
Antes actualiza el clon del canal por fast-forward a origin/main: F2 lo clonó
antes de F4. Una rama distinta de main o cambios tracked bloquean la preparación;
no se resetea ni destruye trabajo. El plan muestra también esa actualización.
No despacha issues ni cambia dispatch.sh.

<!-- terminal: instalador -->
```bash
bash "$PKG/instalacion/scripts/check-F5.sh"
```

## Remediación

| Diagnóstico | Acción |
|---|---|
| usuario ausente | Reabrir F1 y ejecutar el plan de usuarios aprobado. |
| configuración bus distinta: ROL | Repetir F5 con el plan revisado para regenerar runtime.conf del rol; comprobar las tres rutas públicas antes de reiniciar su torre. |
| estado_bus distinto | Reabrir F1 y ejecutar la orden de regeneración indicada; revisar las diferencias y confirmar de nuevo el perfil en F4. Actualizar los clones conservando trabajo antes de repetir F5/F6. |
| clon propio de estación ausente / comando rc test | Crear el clon como M1 y corregir propietario/permisos de su directorio y .git, conservando trabajo. |
| origin estación distinto | Confirmar repo_url y conservar el clon ajeno; usar el clon propio del producto correcto. |
| comando rc tmux / sesión ausente | Entrar como el usuario correcto y revisar la sesión; repetir inicio idempotente. |
| renderer alternativo | Reaplicar install-statusline y reiniciar esa sesión con el env canónico aprobado. |
| barra ctx ausente | Procesar un turno y verificar install-statusline --check-ctx; no asumir 0 %. |
| ERROR resolviendo / registro modelos / modelo de torre | Restaurar el CLI acreditado del usuario indicado y ejecutar resolver-modelos.sh como ese usuario. Cambiar la torre al modelo vigente. Para canales, resolver como C1 y ejecutar preparar-modelo-canal antes de preparar sesiones; repetir check-F5, que exige acreditado con entorno cerrado. Si el selector dejó sonnet después del primer despacho, consultar el doctor de F7 y la orden de preparación anterior; F6–F8 no repiten F5. Golden debe seguir sin credenciales; conservar logins de canales acreditados por F3. El histórico (alias preparado) exige canales sin credenciales; creado exige modelo vacío sin registro. No usar esos modos, IDs manuales ni TC_VERIFY_SCOPE en F5. |
| sesión parada en un aviso | En la terminal del rol, flecha abajo una vez y Enter para aceptar modo sin permisos; después procesar un turno. |
| configuración estación / seal-suite plan | Revisar station.conf y el mapa de identidad generado; confirmar host, clon propio y perfil/ruta del runner. Repetir F5 sin inventar identidades. |
| git sin autenticación | Reabrir F3 y configurar gh auth setup-git; comprobar origin desde el clon propio. |
| gh sin sesión | Completar login del usuario afectado. |
| CodeRabbit CLI ausente | Instalar el CLI en el PATH de M1. |
| CodeRabbit CLI sin autenticación | Revisar la causa y el fichero impresos por la función compartida: clave ausente, serialización, directorio, escritura o estado del CLI. Restaurar la credencial por lectura oculta y repetir F5; no mostrar el valor. |
| sudoers existente distinto | Revisar diff con la persona; no sobrescribir silenciosamente. |
| sesión ausente / consultas sudo no permitidas | Comparar reglas con referencia 07 y su invocación exacta; no autorizar shell arbitrario. |
| identidad/creación de panes de canal fallida | Revisar sesión v, panes .0/.1, cuentas y CLI; restaurar pane indicado con aprobación y repetir preparación. |
| clon no actualizable por fast-forward | Conservar rama/cambios; revisar con responsable y dejar main limpio y actualizable, sin reset destructivo. |
| clon con cambios seguidos / limpieza del clon no verificable | Conservar trabajo; revisar diff y HEAD como el rol indicado. El montaje no debe editar el contrato después de F4. |
| runner correspondencia del motor fallida | Revisar origin público y manifiesto, preflight y herramientas del runner; volver a F2 sin credenciales ni publicación manual. |

## Al terminar

Tres actores en usuarios distintos, panes legibles y barra de contexto visible.
Canales con dev/auditor arrancados e identidad verificada antes de F7.
ORQ/PM son ampliación posterior: cambiar cuestionario, regenerar y reabrir
las fases afectadas; crear usuarios y reglas para sus roles antes de acreditarlos.
No se montan automáticamente en esta topología.
