# F1 — Configuración, credenciales y usuarios previos

## Objetivo

Preparar la configuración declarada y el escrow sin exponer secretos.

## Precondiciones

F0 verde. La persona tiene tokens de GitHub, Linear y CodeRabbit. CodeRabbit
revisa cambios y participa en la puerta de fusión de M1. Esta distribución
trae waive-cr.sh, pero es una exención por PR y SHA con el OK explícito de
la persona, no un modo sin revisor: la clave de CodeRabbit es requisito.
Supabase requiere su token solo si se respondió si.

## Pasos

La persona ejecuta en SU terminal la lectura oculta. Alternativamente edita
ella misma el env creado por --solo-env; nunca usar cat, source ni trazas
sobre ese fichero. El lector solo informa present/missing por nombre.

```bash
bash "$PKG/instalacion/generar-instancia.sh" --respuestas "$R" --salida "$PKG" --home "$H" --solo-env
! bash "$PKG/instalacion/scripts/f1-credenciales.sh"
read -rs -p 'LINEAR_API_KEY: ' LINEAR_API_KEY
export LINEAR_API_KEY
bash "$PKG/instalacion/consultar-estados-linear.sh" --equipo EQUIPO --out "$PKG/instalacion/generado/linear-consulta.json"
unset LINEAR_API_KEY
bash "$PKG/instalacion/generar-instancia.sh" --respuestas "$R" --salida "$PKG" --home "$H" --linear-config "$PKG/instalacion/generado/linear-consulta.json"
```

La primera generación puede sustituir ledger/cuentas.json cuando conserva
exactamente el ejemplo neutro de la distribución; lo anuncia con «sustituye
el ejemplo de la distribución». Cualquier otro ledger distinto del generado
detiene el proceso con rc 3: revise el diff y decida qué versión conservar.
La repetición con las mismas respuestas es idempotente.
La salida de la consulta se crea con modo 0600 en un directorio sin escritura de grupo ni otros.
Si ya existe idéntica y privada, se acepta sin tocarla. Un destino distinto, no regular,
enlace o con permisos inseguros se conserva y devuelve rc 3: use otra ruta de salida
o retire el anterior a mano; después repita la consulta.

La consulta previa de CLAUDE.md escribe linear-consulta.json; el generador
produce linear-instancia.json con el proyecto, sin sobrescribir esa entrada.
La lectura oculta y la consulta de este bloque se ejecutan en la terminal
de la persona, sustituyendo EQUIPO por la clave pública respondida.

El cuestionario registra claude_auth: login por rol o token largo. Para token,
la persona ejecutará claude setup-token en su terminal y entregará el valor por
lectura oculta en F3, por alias de pozo; nunca por argumentos ni por el chat.

El ! representa la terminal interactiva de la persona en Claude Code;
en una terminal normal se omite ese prefijo. El generador conserva el env
existente y escribe el manifiesto, perfil, ledger y agents.conf.

Crear usuarios se adelanta a F1: F2 necesita el operador de Incus, y F3
necesita usuarios de C1/M1 para sus logins. Los nombres vienen de las respuestas.
Al generar, cada rol toma el home real de su cuenta en el sistema; una cuenta
ausente queda prevista en /home/USUARIO y se crea explícitamente con esa ruta.
El perfil confirmado en F4 conserva su estado_bus bajo ese home.
F5/F6 contrastan perfil, home real y runtime.conf; una diferencia exige reabrir
F1, regenerar y confirmar de nuevo en F4, conservando el trabajo de los clones.
Enseña el plan completo y espera visto bueno; después la persona ejecuta:

```bash
bash "$PKG/instalacion/scripts/f5-torres.sh" --plan-usuarios
! sudo bash "$PKG/instalacion/scripts/f5-torres.sh" --usuarios
```

Incus debe estar instalado y existir su grupo incus-admin. No se crea ORQ/PM.
C1 y M1 entran en el mismo grupo: equivale a administrar todos los contenedores.
C1 usa dispatch/relay/capturas; M1 usa gates del motor que llaman a incus,
según talent-merger/references/08-gates-locales.md. Renovar sesiones tras cambios.
M1 necesita escritura en su propio clon y .git; no acceso al estado privado
del instalador ni compartir un checkout mutable entre roles.
El plan concede traversal al grupo dedicado en el home de CEO, sin lectura
de sus ficheros ni cambios de modo en las credenciales.
El paquete y el futuro clon deben permitir lectura y traversal a esos usuarios.
Si están bajo un home privado, la persona decide trasladarlos antes del montaje
o concede acceso al grupo fabrica-PROYECTO. No muevas un paquete ya adjudicado.
Los ficheros de credenciales siguen en 0600, fuera del núcleo.

## Comprobación

check-F1 consulta GitHub sin modificarlo: el token debe leer el repositorio y
tener permisos push y admin (necesario en F4). Consulta también identidad y
equipo en Linear. Los valores viajan por entorno o cabecera privada 0600,
nunca en argumentos ni salida. CODERABBIT_API_KEY no tiene una comprobación
barata sin efectos; su capacidad real se verifica durante el ciclo de F8.

```bash
bash "$PKG/instalacion/scripts/check-F1.sh"
```

## Remediación

| Diagnóstico | Acción |
|---|---|
| Linear: token rechazado | Caso HTTP 401/403: sustituir el token en privado y repetir la consulta. |
| Linear: consulta rechazada por el servicio | Caso HTTP 400 con errors o errors en HTTP 200: conservar código y mensaje públicos para revisar la consulta; no avanzar. |
| Linear: límite de peticiones | Caso HTTP 429: esperar y repetir la consulta. |
| Linear: sin conexión | Caso red o tiempo agotado: restaurar conectividad y repetir la consulta. |
| Linear: equipo EQUIPO no encontrado con este token | Caso equipo ausente: corregir clave pública o permisos y repetir la consulta. |
| Linear: tope de 20 páginas | Caso hasNextPage tras veinte páginas: detenerse y revisar el volumen; no usar la salida incompleta. |
| Linear: paginación inválida | Caso cursor ausente o repetido: revisar la respuesta del servicio antes de repetir. |
| credenciales missing | La persona rellena el nombre indicado con lectura oculta; repetir F1. |
| GITHUB_TOKEN: rechazado | La persona sustituye la credencial en su fichero privado y repite F1. |
| git-bootstrap-token: distinto de GITHUB_TOKEN | Actualizar también el token de bootstrap en el escrow privado, con modo 0600; repetir F1 antes de provisionar. |
| GITHUB_TOKEN: sin permiso push sobre el repositorio | Autorizar escritura en el repositorio declarado y repetir F1. |
| GITHUB_TOKEN: sin permiso admin sobre el repositorio | Autorizar administración para aplicar protección de rama en F4. |
| LINEAR_API_KEY: rechazada | Sustituir la clave en privado y repetir F1. |
| LINEAR_API_KEY: equipo declarado ausente | Corregir permisos o equipo declarado mediante el cuestionario. |
| sin red | Restaurar conectividad de los clientes y repetir; no asumir credencial válida. |
| modo 0600 / propietario | La persona restaura 0600 y propietario CEO, sin mostrar contenido. |
| escrow vacío / pieza ausente | Repetir f1-credenciales en terminal; necesita git-bootstrap-token y cuser-pass para golden. |
| escrow: formato inválido | La persona corrige asignaciones NOMBRE=valor únicas, sin imprimirlas. |
| colisión del generador (rc 3) | Revisar solo el diff público; no usar --forzar hasta resolver autoridad. |
| rechazo del generador | Corregir la respuesta por cuestionario; no alterar el generador. |
| configuración: manifiesto/agents.conf incoherente o pieza ausente | Regenerar desde respuestas completas; resolver diferencias antes de forzar. |
| usuario ausente / sin grupo de fábrica / sin incus-admin | Repetir plan-usuarios aprobado y renovar login; no abrir estado privado. |
| perfil/manifiesto/ledger rojo | Resolver diagnósticos públicos de los validadores reales y regenerar coherentemente. |

## Al terminar

Configuración completa, secretos privados y usuarios de sistema disponibles.
